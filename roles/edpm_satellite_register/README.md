# edpm_satellite_register

Appends a Satellite global-registration command to an EDPM
`OpenStackDataPlaneNodeSet`'s `edpm_bootstrap_command` **without overwriting**
whatever that field already contains.

## Why this role exists

The EDPM nodeset `edpm_bootstrap_command` is a single scalar field. In the
`satellite-integration-*` jobs two independent kustomize overlays both set it:

- the Satellite registration overlay
  (`cifmw_architecture_user_base64_kustomize`, generated by the
  `rhos-qe-jenkins` satellite flow), and
- the catalog registry-mirror fallback
  (`cifmw_architecture_user_kustomize_97_catalog_registry`, produced by the
  components-integration catalog tooling).

Kustomize (and JSON6902) cannot *append* to a scalar — `add`/`replace` on an
existing string overwrites it — so the two overlays collide and one silently
drops the other. When the registration command is the one dropped, the compute
nodes never register to the Satellite, RHEL BaseOS/AppStream are unavailable,
and `edpm_bootstrap` fails `dnf` depsolve (`container-selinux`, `lvm2`, ...).

This role reads the current `edpm_bootstrap_command` from the live nodeset and
appends the registration command to it, so both snippets coexist. It is the
single owner of the registration fragment: adding another concern later means
another small appender, not duplicating the whole command. The approach mirrors
`roles/fdp_update_edpm/tasks/configure_ca_cert.yml`, which appends CA-cert setup
to the same field.

## Parameters

| Variable | Default | Description |
|---|---|---|
| `cifmw_edpm_satellite_register_command` | `""` | The Satellite global-registration command (`curl ... \| bash`) to append. **Required.** Sourced from the Satellite registration API (see `rhos-qe-jenkins` `infra/satellite/tasks/prepare_deployment_data.yml`). |
| `cifmw_edpm_satellite_register_nodeset_name` | `openstack-edpm` | Name of the `OpenStackDataPlaneNodeSet` to patch. |
| `cifmw_edpm_satellite_register_namespace` | `openstack` | Namespace of the nodeset. |
| `cifmw_edpm_satellite_register_dry_run` | `false` | Compute the patched command but do not patch the nodeset. |

## Idempotency

The role detects the `register?activation_keys` marker in the existing command
and skips the patch when the registration is already present, so it is safe to
re-run.

## Ordering

The role must run **after** the nodeset exists and after any other overlay that
sets `edpm_bootstrap_command` has been applied, and **before** the `bootstrap`
dataplane service runs. In the standard flow this is the `post_stage` hook of
the EDPM nodeset stage (e.g. `edpm-pre-ceph-nodeset`), which runs after that
stage applies the CR and before the deployment stage runs the services.

To catch a misplaced hook, the role fails loudly if:

- the target nodeset does not exist yet (hook ran too early), or
- the nodeset already reports `DeploymentReady=True` (hook ran too late — the
  bootstrap service has already consumed `edpm_bootstrap_command`, so appending
  would have no effect).

## Testing

This role is not tested via Molecule: it only patches a live
`OpenStackDataPlaneNodeSet` on a running OpenShift cluster (via
`kubernetes.core.k8s`), which Molecule cannot provide. The `molecule/`
directory has therefore been removed and `make role_molecule` regenerated the
Zuul job definitions accordingly.
